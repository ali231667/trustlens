### `data_ingestion.py`
Three functions, all using RapidAPI's "Instagram Scraper Stable API":

**Fixed a real bug that caused a 7-minute hang on a live scan:** none of these three calls had a `timeout` set. ### Email verification at signup — NOT repeated 2FA (redesigned 2026-09-24, corrects the first version built earlier the same night)
**Important terminology correction, for anyone reading this or defending it to the panel:** the first version of this feature made every single login require a fresh emailed code — that's genuine, textbook "2FA." Hamza tested it, decided that's the wrong UX for this app ("it doesn't make sense... that would be totally useless" — his words), and asked for the standard alternative instead: **verify the email once, at signup, then password-only login forever after.** That's a real, common, different pattern usually called **email verification**, not 2FA. Both are legitimate; they are not the same feature. If the panel asks "is this 2FA," the honest, correct answer is **no** — it's one-time email verification, and that distinction should be stated plainly, not blurred.

**Why this redesign, driven by two things Hamza caught by testing, not by inspection:**
1. **A fake/nonexistent email sailed through signup with zero problem** under the old design, because 2FA-at-login never touches signup at all — signup only ever validated email *format* (has an `@`, has a dot), never that the mailbox is real. Verifying at signup closes this: a fake address can receive a code that never arrives, so that account can **never** complete verification, so it can **never** be used to log in — even though (confirmed by live testing) Gmail doesn't always reject a fake recipient synchronously at send-time, especially outside its own domain, so the signup response can't always *say* "this email doesn't exist" immediately. The account being permanently unusable is the real, achieved guarantee — not an immediate rejection message, which would need a paid real-time email-verification API (same billing-risk shape as things already avoided in this project).
2. **Password strength wasn't checked at all** — only length (≥8 chars). `"12345678"` passed. `auth.py`'s `password_strength_error()` now also requires at least one letter and one digit (deliberately not stricter than that — special-character requirements would be overkill for a student project login, not a bank). `SignUp.jsx` mirrors the exact same rule client-side for an instant Weak/Medium/Strong meter (`passwordStrength()` in that file) so what the user sees live matches what the server will actually accept, not a guess.

**Flow:**
1. `POST /signup` — creates the account with `email_verified=False`, generates a code (`auth.py`'s `generate_verification_code()`, uses `secrets.randbelow`, not `random`), stores it in `database.py`'s `VerificationCode` table (user_id, code, expires_at, used — DB-backed, not in-memory, because this backend has repeatedly needed full restarts during development and an in-memory store would silently wipe pending codes on every one) with a 10-minute expiry, emails it via `email_service.send_2fa_code()`.
2. `POST /verify-email` — checks the code, sets `email_verified=True` **permanently**, issues the token immediately (auto-login right after verifying — no need to re-enter the password).
3. `POST /login` on an already-verified account — password check only, token issued directly, no code, ever again.
4. `POST /login` on a **never-verified** account (e.g. they closed the tab mid-signup) — password is still checked first, then a **fresh** code is sent and `requires_verification` is returned again, so they're never permanently stuck, just redirected back into the same verification step.

**`email_configured()` guard unchanged in spirit**: if `GMAIL_ADDRESS`/`GMAIL_APP_PASSWORD` aren't set, signup fails loudly with a clear 503 rather than silently creating an unusable/unverifiable account — matches this project's "never fake it" rule. (As of this redesign, both are filled in with Hamza's real values, so this path is no longer hit in normal use — documented for completeness.)

**Verified live against the real running server** (not the old 2FA-at-login tests, which are obsolete — this is the new flow, retested from scratch): password `"12345678"` (all digits) rejected — "must include at least one letter"; `"abcdefgh"` (all letters) rejected — "must include at least one number"; signup with a real strong password but a syntactically-valid-but-nonexistent `@gmail.com` address **succeeded** (account created, code "sent") but that account **could never log in** — confirmed by then calling `/login` on it, which correctly detected `email_verified=False` and resent a code rather than granting access, proving the account is permanently gated regardless of the send-time response. Full real loop also retested: signup → grabbed the real generated code directly from the DB (same trick used to avoid needing a live inbox for every single test) → `/verify-email` → real token issued → **called `/login` again with the same credentials → token issued directly, no code requested** — confirming the core behavior Hamza asked for. **THE REAL BUG (diagnosed correctly on the third report — read this before trusting the "race condition" write-up below it).** Symptom Hamza hit three separate times with three different emails: correct code entered → "Incorrect or expired code" on screen → but the database showed `used=True` and `email_verified=True` every single time. **Actual root cause: after successful verification, nothing navigated anywhere.** `VerifyCodeForm` called `verifyCode()`, which logged the user in via AuthContext — and then the screen just sat there, unchanged. A code comment in that file even claimed "the parent page's own auth-aware redirect handles navigation from here," but **that redirect had never been written** in either `Login.jsx` or `SignUp.jsx`. So a successful verification looked like a no-op, the user naturally clicked "Verify & continue" again, and *that second click* legitimately failed on an already-used code — which is the error that ended up on screen. **Fix**: both `Login.jsx` and `SignUp.jsx` now short-circuit with `if (user) return <Navigate to="/dashboard" replace />`, so the instant AuthContext sets `user`, the page redirects. One mechanism, covers every success path (fresh signup verification, unverified-account login recovery, and plain password login).

**Process lesson worth keeping:** the first two diagnoses of this bug were wrong (stale Vite bundle; then a double-click race condition). Both were plausible, both were even partially real, and neither was the actual cause — the giveaway that should have been caught sooner was that *the database showed success every time*, which meant the failing thing was the UI's response to success, not the verification itself. When a backend says yes and a screen says no, suspect the screen.

**Secondary issue, also real, also fixed (was NOT the main cause):** a genuine double-submission race on the code form. Symptom overlapped with the above: correct code, "Incorrect or expired code" on screen, account actually fine. Diagnosed by checking the database directly rather than guessing: both times, `VerificationCode.used` was already `True` and `User.email_verified` was already `True` — the verification had genuinely succeeded, but the UI still showed a failure. **Root cause, reproduced on demand**: the submit button's `disabled={loading}` guard relies on a React state update, which isn't synchronous — a fast double-click (or Enter-then-click) fires `handleSubmit` twice before the button visually disables, sending two `/verify-email` requests with the same code. The first one correctly marks the code used and logs the account in; the second, arriving a moment later, correctly gets rejected ("already used") — and if that second response resolves after the first, its failure message is what's left on screen, even though verification already succeeded. **Confirmed by literally firing two simultaneous curl requests with the same real code at the backend** — reproduced the exact split result (one token, one "Incorrect or expired code") on demand, proving this diagnosis rather than assuming it.

**Fix**: added a `useRef`-based `submittingRef` guard to `VerifyCodeForm.jsx`, `Login.jsx`, and `SignUp.jsx`'s submit handlers — a ref updates immediately (unlike state), so it actually blocks a second call within the same tick instead of just visually disabling a button a few milliseconds too late. Applied to all three forms consistently, not just the one that was reported, since they all had the identical vulnerability.

**Practical note for anyone testing this project**: if a "wrong code" error ever looks suspicious, check the database directly before assuming the code was actually wrong — `SELECT` the user's `email_verified` and the `VerificationCode` row for that exact code; if both show success, the account is fine and it's a display-timing issue like this one, not a real rejection. ### The zero trust score — real bug, found 2026-09-24, in `CountUp.jsx`
**Symptom:** the Results page showed a Trust Score of **0.0** while the ring beside it drew ~78% full and the verdict read **"Trusted"**. Reported twice; the first time it was misdiagnosed as a backend problem and chased through the database and the scoring maths, both of which were always correct.

**Root cause: React StrictMode + a "only animate once" ref guard.** `main.jsx` wraps the app in `<StrictMode>`, which in development deliberately runs every effect twice — mount, cleanup, mount again — precisely to expose effects that aren't safe to re-run. `CountUp` had a `startedRef` guard, so the sequence was:
1. first run — `startedRef` flips to `true`, animation timer scheduled
2. cleanup — `clearTimeout` cancels that timer
3. second run — `startedRef` is already `true`, returns early, **never reschedules**

So `display` stayed at its initial `0` forever and rendered `"0.0"`. **Every `CountUp` on the site was affected** (Results score, Landing trust strip, Dashboard totals, About and Methodology stat banners) — the reason it was most obvious on Results is that a big fat `0.0` sat directly next to a correctly-drawn ring and a "Trusted" verdict.

**The clincher, in the same file:** the ring's own effect (`Results.jsx`, the `setTimeout(() => setRingOffset(...), 200)`) has **no** ref guard, so StrictMode re-runs it and it works. Same page, same render, same data — the one with the guard broke, the one without it didn't.

**Fix:** the guard is gone. Re-running the animation on a remount is harmless because it always lands on the same final value, so the guard bought nothing and cost this. The effect now also cancels its `requestAnimationFrame` (not just the `setTimeout`) on cleanup, and renders `0` rather than `NaN` if it is ever handed a non-numeric value. **Rule for any future animation effect in this project: do not add a once-only ref guard to an effect. If an effect must not be re-run, make it idempotent instead.**

**Two debugging traps worth remembering (both cost time this session):**
1. **`typeof TL` in the DevTools console returns `undefined` even when the extension is working perfectly.** Content scripts run in an isolated world; the default console context is the *page's* world. To check properly, switch the context dropdown (the one labelled `top`) to "TrustLens — Instagram Authenticity Checker".
2. **`TL.log` uses `console.debug`, which Chrome hides** unless the log-level dropdown has **Verbose** ticked. A working extension looks completely silent under "Default levels".
Also: content scripts only inject into tabs loaded *after* the extension is installed — an already-open Instagram tab needs a reload.

**In-app Extension page (added 2026-09-24, supervisor's request).** M. Zulfiqar Khan asked that the extension be reachable from the platform rather than being a separate thing the user wanders off to. `/extension` (navbar: "Extension") now holds: **live service status** polled from the gateway's own `/health` (green/red dot per service, plus a "Re-check services" button), a one-click **"Open Instagram in a new tab"**, the five-step Chrome install guide, and a plain-language explanation of what the badge checks. `getExtensionStatus()` in `api/trustlens.js` does the polling — it never throws (the gateway not running is the normal case, not an error) and has a 3s abort timeout so the page can't hang when nothing is listening on 8100.

**Instagram genuinely cannot be embedded in the page** — it sends `X-Frame-Options`/`frame-ancestors` headers that forbid framing by other origins, enforced browser-side as an anti-clickjacking control. There is no front-end workaround, and anything that looked like one would be a fake screenshot rather than the live site. Opening in a new tab keeps TrustLens open in the original tab, which achieves the same "never lose the platform" outcome. **Say this plainly if the panel asks why it isn't embedded** — it's a platform security control, not a shortcut.

**Real bug found while building that page — the gateway lied about the transcriber being up.** `clients.py`'s `_probe()` used `up = r.status_code < 500`, so a **404 counted as "up"**. That is not hypothetical: the transcriber's default port **8000 is the same port the main TrustLens website runs on**, so with the website running, the gateway probed it, got the website's own 404, and reported "transcriber: up". The extension would then show a "Listen to audio" button that could only ever fail. Fixed to `< 400` — a 404 means that health path doesn't exist, so something *else* is answering on that port. Verified live: the same probe now correctly returns `{"up": false, "status_code": 404}` while classifier and account model stay `{"up": true, "status_code": 200}`.

**Honest gaps:** the scope doc says the extension "also works on TikTok's web interface" — it does **not**; `manifest.json` matches `instagram.com` only and the DOM parser is Instagram-specific. Do not claim TikTok support.
