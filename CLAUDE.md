### `data_ingestion.py`
Three functions, all using RapidAPI's "Instagram Scraper Stable API":

**Fixed a real bug that caused a 7-minute hang on a live scan:** none of these three calls had a `timeout` set. In Python, `requests` with no timeout waits *indefinitely* if the connection stalls — and this network has repeatedly shown itself to stall over the course of this project. All three now have explicit timeouts (20s / 20s / 15s) with clear error messages on timeout, so a scan's worst case is bounded to well under a minute instead of hanging forever. **Verified live**: a real scan of `cristiano` (Cristiano Ronaldo, 679M followers) completed in 20 seconds after this fix, down from the 7-minute hang reported before it.

### Email verification at signup — NOT repeated 2FA (redesigned 2026-09-24, corrects the first version built earlier the same night)
**Important terminology correction, for anyone reading this or defending it to the panel:** the first version of this feature made every single login require a fresh emailed code — that's genuine, textbook "2FA." Hamza tested it, decided that's the wrong UX for this app ("it doesn't make sense... that would be totally useless" — his words), and asked for the standard alternative instead: **verify the email once, at signup, then password-only login forever after.** That's a real, common, different pattern usually called **email verification**, not 2FA. Both are legitimate; they are not the same feature. If the panel asks "is this 2FA," the honest, correct answer is **no** — it's one-time email verification, and that distinction should be stated plainly, not blurred.

**Why this redesign, driven by two things Hamza caught by testing, not by inspection:**
1. **A fake/nonexistent email sailed through signup with zero problem** under the old design, because 2FA-at-login never touches signup at all — signup only ever validated email *format* (has an `@`, has a dot), never that the mailbox is real. Verifying at signup closes this: a fake address can receive a code that never arrives, so that account can **never** complete verification, so it can **never** be used to log in — even though (confirmed by live testing) Gmail doesn't always reject a fake recipient synchronously at send-time, especially outside its own domain, so the signup response can't always *say* "this email doesn't exist" immediately. The account being permanently unusable is the real, achieved guarantee — not an immediate rejection message, which would need a paid real-time email-verification API (same billing-risk shape as things already avoided in this project).
2. **Password strength wasn't checked at all** — only length (≥8 chars). `"12345678"` passed. `auth.py`'s `password_strength_error()` now also requires at least one letter and one digit (deliberately not stricter than that — special-character requirements would be overkill for a student project login, not a bank). `SignUp.jsx` mirrors the exact same rule client-side for an instant Weak/Medium/Strong meter (`passwordStrength()` in that file) so what the user sees live matches what the server will actually accept, not a guess.

**Flow:**
1. `POST /signup` — creates the account with `email_verified=False`, generates a code (`auth.py`'s `generate_verification_code()`, uses `secrets.randbelow`, not `random`), stores it in `database.py`'s `VerificationCode` table (user_id, code, expires_at, used — DB-backed, not in-memory, because this backend has repeatedly needed full restarts during development and an in-memory store would silently wipe pending codes on every one) with a 10-minute expiry, emails it via `email_service.send_2fa_code()`.
2. `POST /verify-email` — checks the code, sets `email_verified=True` **permanently**, issues the token immediately (auto-login right after verifying — no need to re-enter the password).
3. `POST /login` on an already-verified account — password check only, token issued directly, no code, ever again.
4. `POST /login` on a **never-verified** account (e.g. they closed the tab mid-signup) — password is still checked first, then a **fresh** code is sent and `requires_verification` is returned again, so they're never permanently stuck, just redirected back into the same verification step.

**`email_configured()` guard unchanged in spirit**: if `GMAIL_ADDRESS`/`GMAIL_APP_PASSWORD` aren't set, signup fails loudly with a clear 503 rather than silently creating an unusable/unverifiable account — matches this project's "never fake it" rule. (As of this redesign, both are filled in with Hamza's real values, so this path is no longer hit in normal use — documented for completeness.)

**THE REAL BUG (diagnosed correctly on the third report — read this before trusting the "race condition" write-up below it).** Symptom Hamza hit three separate times with three different emails: correct code entered → "Incorrect or expired code" on screen → but the database showed `used=True` and `email_verified=True` every single time. **Actual root cause: after successful verification, nothing navigated anywhere.** `VerifyCodeForm` called `verifyCode()`, which logged the user in via AuthContext — and then the screen just sat there, unchanged. A code comment in that file even claimed "the parent page's own auth-aware redirect handles navigation from here," but **that redirect had never been written** in either `Login.jsx` or `SignUp.jsx`. So a successful verification looked like a no-op, the user naturally clicked "Verify & continue" again, and *that second click* legitimately failed on an already-used code — which is the error that ended up on screen. **Fix**: both `Login.jsx` and `SignUp.jsx` now short-circuit with `if (user) return <Navigate to="/dashboard" replace />`, so the instant AuthContext sets `user`, the page redirects. One mechanism, covers every success path (fresh signup verification, unverified-account login recovery, and plain password login).

**Process lesson worth keeping:** the first two diagnoses of this bug were wrong (stale Vite bundle; then a double-click race condition). Both were plausible, both were even partially real, and neither was the actual cause — the giveaway that should have been caught sooner was that *the database showed success every time*, which meant the failing thing was the UI's response to success, not the verification itself. When a backend says yes and a screen says no, suspect the screen.

**Secondary issue, also real, also fixed (was NOT the main cause):** a genuine double-submission race on the code form. Symptom overlapped with the above: correct code, "Incorrect or expired code" on screen, account actually fine. Diagnosed by checking the database directly rather than guessing: both times, `VerificationCode.used` was already `True` and `User.email_verified` was already `True` — the verification had genuinely succeeded, but the UI still showed a failure. **Root cause, reproduced on demand**: the submit button's `disabled={loading}` guard relies on a React state update, which isn't synchronous — a fast double-click (or Enter-then-click) fires `handleSubmit` twice before the button visually disables, sending two `/verify-email` requests with the same code. The first one correctly marks the code used and logs the account in; the second, arriving a moment later, correctly gets rejected ("already used") — and if that second response resolves after the first, its failure message is what's left on screen, even though verification already succeeded. **Confirmed by literally firing two simultaneous curl requests with the same real code at the backend** — reproduced the exact split result (one token, one "Incorrect or expired code") on demand, proving this diagnosis rather than assuming it.

**Fix**: added a `useRef`-based `submittingRef` guard to `VerifyCodeForm.jsx`, `Login.jsx`, and `SignUp.jsx`'s submit handlers — a ref updates immediately (unlike state), so it actually blocks a second call within the same tick instead of just visually disabling a button a few milliseconds too late. Applied to all three forms consistently, not just the one that was reported, since they all had the identical vulnerability.

**Practical note for anyone testing this project**: if a "wrong code" error ever looks suspicious, check the database directly before assuming the code was actually wrong — `SELECT` the user's `email_verified` and the `VerificationCode` row for that exact code; if both show success, the account is fine and it's a display-timing issue like this one, not a real rejection. Both of Hamza's real test accounts from this incident (`231649@students.au.edu.pk`, `231556@students.au.edu.pk`) are confirmed genuinely verified in the database — no need to re-signup or reset either one.

Frontend: `frontend/src/context/AuthContext.jsx` holds the logged-in user app-wide (React Context), persists the token in `localStorage` under `trustlens_token`, and validates it against `/me` on every page load. `Navbar.jsx` reads this to show "Log in" vs. the user's name + "Log out" — this is what fixed the earlier confusing bug where the navbar always said "Log in" even while using the app, because no real session existed to check yet.

**Edge-case hardening pass (2026-09-24)**, done specifically because Hamza flagged that the panel might deliberately try wrong/malformed credentials. Tested live against the real running server (not guessed): invalid email format, empty fields, missing JSON body, duplicate signup email, wrong password, nonexistent login email, different-case email at login (correctly still works — email is lowercased on both signup and login) — all already handled cleanly. **Found and fixed a real crash**: a password longer than 72 bytes (bcrypt's hard limit) caused an unhandled `ValueError` → raw `Internal Server Error` (500) on **both** `/signup` and `/login`, confirmed by deliberately testing a 500-character password against the live server before fixing. Fix, defense in depth: `MAX_PASSWORD_BYTES = 72` in `auth.py`, checked explicitly at signup (`main.py`, clean 400 "Password must be 72 characters or fewer") so no account can ever be created with an unhashable password; `verify_password()` also independently wraps `bcrypt.checkpw` in try/except and returns `False` on `ValueError` instead of raising, so login can never crash on this regardless of what's already in the database. Frontend `SignUp.jsx` password field also got `maxLength={72}` to match. **Note for next session:** if this server is running with `--reload` and edits don't seem to take effect, don't assume the fix is wrong — kill and restart fully; reload didn't pick up a `main.py` change during this exact testing pass.

### `fake_follower.py`

#### CRITICAL BUG FOUND AND FIXED 2026-09-24 — the model was silently non-functional
**Read this before quoting any accuracy number for this module.** The old `fake_follower_model.pkl` **predicted "genuine" for every single account it was ever given.** Not most — all. Verified against 696 labelled accounts already sitting in this repo (`archive/fake_follower_detection_ali/goyal-dataset/`): 0 of 576 training rows and 0 of 120 test rows were ever predicted fake, giving exactly 50% accuracy on a balanced set. **Root cause, proven not guessed:** the original training notebook (`archive/misc/TrustLens_Implementation.ipynb`) does `scaler = StandardScaler(); X_scaled = scaler.fit_transform(X)` — it trained on **standardised** features but pickled **only the model, never the scaler**, while `fake_follower.py` fed it **raw** values. **Fix:** new `backend/train_fake_follower.py` retrains on a dataset that IS in the repo, uses **no scaler at all** (a Random Forest splits on thresholds and never needed one — this removes the entire bug class permanently), imports `build_features()` from `fake_follower.py` so training and inference can never drift again, and refuses to save a model that only predicts one class. **Real result: 95.8% on the held-out test set** (precision/recall ≈0.95-0.97 on both classes; TP 58, FP 3, FN 2, TN 57). 95.8% is lower than the old claim but it is real, reproducible by anyone with `python train_fake_follower.py`, and defensible. **All frontend copy was updated from 99.3% → 95.8%** (AuthPanel, About, Landing, Methodology). Old broken model kept at `fake_follower_model.broken-scaler-backup.pkl`.

**Known honest limitation of the retrained model:** genuinely new/small real accounts (e.g. 30 followers, 4 posts, but with a real picture and bio) score high on bot probability, because the training data's "genuine" examples are mostly established accounts. Say this plainly if asked rather than hiding it.

### `trust_score.py`
`calculate_trust_score(bot_percentage, engagement_score, misinfo_result=None, credential_result=None)` — **redesigned 2026-09-24: no placeholder score anywhere, ever** (Hamza's explicit instruction — the old design filled unused weight with a flat neutral 70, which he correctly identified as a second, disguised version of the exact same "fake number" problem he'd already caught once with the deepfake removal). ### Misinformation Classifier (`backend/misinfo_classifier/`)
This was originally a teammate's (Umar's) module, shared via Google Drive with a claimed "75% accuracy" — that number turned out to be measured on training/validation data, not a genuine held-out test set, so it was untrustworthy. The code itself (`prepare_data.py`, `train_model.py`, `model_loader.py`) was reviewed and judged genuinely well-built — the fix needed was to the **dataset composition and the retraining process**, not a rewrite.

**Dataset (`unified_dataset.csv`, 46,392 rows, 6 classes):**
- `credible` (0) — baseline/non-misinformation examples from all sources below
- `health_misinformation` — CoAID (COVID-19 news/claims only — this is the source of a known weakness, see Limitations)
- `political_propaganda` — LIAR (short political statements, 6-way truthfulness scale collapsed to binary: pants-fire/false/barely-true → 1, half-true/mostly-true/true → 0)
- `financial_scam` — SMS Spam Collection used as a linguistic proxy (no real Instagram-scam dataset exists freely) — documented as a known limitation
- `sensational_clickbait` — FakeNewsNet, **titles only** (not full articles — those need live scraping via dead 2018-era URLs, not worth it; headlines alone are a standard valid basis for clickbait detection)
- `urdu_misinformation` — UrduFake ("Bend the Truth" dataset) — **given its own category**, not merged into political_propaganda, because an earlier attempt to merge it hurt accuracy (LIAR's short English claims and UrduFake's full Urdu articles are stylistically too different to share a class well)

### The zero trust score — real bug, found 2026-09-24, in `CountUp.jsx`
**Symptom:** the Results page showed a Trust Score of **0.0** while the ring beside it drew ~78% full and the verdict read **"Trusted"**. Reported twice; the first time it was misdiagnosed as a backend problem and chased through the database and the scoring maths, both of which were always correct.

**Root cause: React StrictMode + a "only animate once" ref guard.** `main.jsx` wraps the app in `<StrictMode>`, which in development deliberately runs every effect twice — mount, cleanup, mount again — precisely to expose effects that aren't safe to re-run. `CountUp` had a `startedRef` guard, so the sequence was:
1. first run — `startedRef` flips to `true`, animation timer scheduled
2. cleanup — `clearTimeout` cancels that timer
3. second run — `startedRef` is already `true`, returns early, **never reschedules**

So `display` stayed at its initial `0` forever and rendered `"0.0"`. **Every `CountUp` on the site was affected** (Results score, Landing trust strip, Dashboard totals, About and Methodology stat banners) — the reason it was most obvious on Results is that a big fat `0.0` sat directly next to a correctly-drawn ring and a "Trusted" verdict.

**The clincher, in the same file:** the ring's own effect (`Results.jsx`, the `setTimeout(() => setRingOffset(...), 200)`) has **no** ref guard, so StrictMode re-runs it and it works. Same page, same render, same data — the one with the guard broke, the one without it didn't.

**Fix:** the guard is gone. Re-running the animation on a remount is harmless because it always lands on the same final value, so the guard bought nothing and cost this. The effect now also cancels its `requestAnimationFrame` (not just the `setTimeout`) on cleanup, and renders `0` rather than `NaN` if it is ever handed a non-numeric value. **Rule for any future animation effect in this project: do not add a once-only ref guard to an effect. If an effect must not be re-run, make it idempotent instead.**

It also **missed** 3 of 8 real scams ("this herb cures diabetes", "guaranteed 50% monthly returns", "lose 20kg in 10 days"). **Fix — `backend/misinfo_assessment.py`:** a "financial_scam" label only counts when a hard red flag backs it (guaranteed returns, impossible claims, disguised links, named-disease cures); a hard red flag counts even if the model said credible (risk floored at 85); other classes are used as the model gives them (no evidence of a problem there, so nothing changed). Controlled result: false alarms **8 → 0**, real scams caught **5 → 7 of 8**. **Honest caveat:** I wrote both the red-flag regexes and those 8 test scams, so 7/8 is optimistic; the trustworthy evidence is that it removes the real false alarms from real scans. The proper fix is retraining that class on real Instagram scam-vs-promo data, which doesn't exist publicly — say this is the documented limitation. The rules come from `backend/red_flags.py`, **moved out of the extension folder so the website and extension share one rule set** (they previously disagreed about the same caption). The Results page openly shows when AI "scam" labels were set aside and why.
2. **Engagement — missing data scored as bad engagement.** Real scan #3 of @hamza_clipss got **0 posts back** from Instagram (a hiccup) → averaged to 0 likes → "Suspicious" → 69.8 Moderate Risk for a 22%-engagement account. **Fix:** `posts_analyzed == 0` → "Not measured", left out of the Trust Score (like misinformation with no text). That scan now reads 95.8 Trusted.
3. **Engagement — cliff edges.** 4-step staircase: a 500k account at 0.74% scored 20, at 0.75% scored 50 (~8 Trust Score points from 0.01%). **Fix:** smooth curve through (ratio→score) (0,5) (0.5,35) (1.0,65) (1.5,85) (2.5,95), which passes exactly through the old step values at the middle of each old band, so scores don't shift on average. Band labels (Excellent/Healthy/Below Average/Suspicious) unchanged. **Remaining honest gap:** the benchmark rates (Nano 5%, Micro 3%, Macro 1.5%, Mega 0.8%) have no documented source in this repo.
4. **Credential Extractor — innocent bios claiming credentials.** Case-insensitive "rd"/"md" matched "Mall **Rd**, Lahore" → Registered Dietitian, "**Md.** Usman" (Muhammad) → MD, "**MD** of my startup" (Managing Director) → MD — and those accounts then LOST points for an unverified medical claim. **Fix:** short abbreviations are case-sensitive and only count in qualification form ("Sara Khan, RD", "M.D.", "Dr. Ahmed"); full phrases still match in any case.
5. **Fake-account model — mislabelled, and missing inputs.** It judges the account's OWN profile; the site said "Followers analyzed: 536,885" and "Follower authenticity". Relabelled everywhere (Results, Comparison, Landing, About, AuthPanel, Methodology, admin) to "Account Authenticity" / "Fake-account likelihood" / "Follower count". It was also trained on four name features (username digit ratio, full-name word count, full-name digit ratio, name==username) that the site never passed — now computed by `fake_follower.name_features()` from data every scan already has. Inputs are now passed as named columns (removes a per-prediction scikit-learn warning). **Known limitation unchanged:** genuinely new small accounts score bot-like.
6. **Results page colours were hard-coded green** — "Suspicious" engagement rendered green; a 98%-fake account would have too. Now follows each module's verdict.
